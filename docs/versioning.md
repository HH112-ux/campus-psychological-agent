# 版本与发布策略

本仓库采用语义化版本（SemVer）：`MAJOR.MINOR.PATCH`。

## 1. 版本规则

| 版本段 | 何时递增 | 示例 |
|---|---|---|
| MAJOR | 提审/正式上线、破坏性变更、产品方向变更 | 1.0.0 = 首次提审版本 |
| MINOR | 新增向后兼容的功能（对应新 F 功能或新接口） | 0.1.0 → 0.2.0 |
| PATCH | 缺陷修复、文档、内部重构（行为不变） | 0.1.0 → 0.1.1 |

- 开发期（0.x）：功能新增升 MINOR，修复升 PATCH。
- 1.0.0 与"提审上线"绑定；进入 1.x 后，任何破坏性变更必须升 MAJOR 并在提交信息标注 `BREAKING CHANGE:`。

## 2. Tag 规则（与里程碑分工）

| Tag 类型 | 用途 | 示例 |
|---|---|---|
| `m0`–`m5` | 开发里程碑（对齐《开发文档》演示节点，验收即打） | `m1`、`m3` |
| `vX.Y.Z` | 可发布/可提审版本 | `v0.1.0`、`v1.0.0` |

- 里程碑 tag 证明"阶段验收通过"，版本 tag 证明"可交付状态"。
- 发版时在 main 上打 `vX.Y.Z`，并同步更新 `CHANGELOG.md`（把 Unreleased 段落归入该版本）。

## 3. 发版检查清单（打 v 版本前）

- [ ] 里程碑验收对应通过
- [ ] CHANGELOG 已更新
- [ ] 危机测试集全量通过（召回不降）
- [ ] 后端 pytest 全绿；小程序代码质量检查无 error
- [ ] 无未合入的待办功能；.env/密钥确认未入库

## 4. 历史版本维护

- 0.x 阶段不做长期分支维护：发现回归直接修复并升 PATCH。
- 进入 1.x 后，如需支持旧版本，从对应 tag 切 `release/<major>.<minor>` 分支，仅合修复。
