# 任务拆分规范

把《开发文档》的功能需求（F1–F6）拆成可独立开发、独立验收的最小任务单元，每条任务与阶段、接口契约一一对应，保证 8 周进度可追踪。

## 1. 任务编号

格式：`<功能编号>-<序号>`，功能编号对齐《开发文档》功能总表（F1 首页打卡 / F2 对话陪伴 / F3 情绪识别 / F4 危机干预 / F5 情绪日志 / F6 账户数据），另加 `T` 开头的基础任务（工程/基建/合规）。

示例：

| 编号 | 标题 | 阶段 | 关联接口（API 文档） |
|---|---|---|---|
| T-01 | FastAPI 脚手架与 /health | P0 | — |
| T-02 | MongoDB 建库建集合与索引 | P0 | — |
| F2-01 | 微信登录换取 JWT 全链路 | P1 | POST /auth/wx-login、POST /auth/refresh |
| F2-02 | 会话创建/列表/详情/重命名/删除 | P1 | /sessions 系列 |
| F2-03 | 消息发送（非流式） | P1 | POST /sessions/{id}/messages |
| F2-04 | 流式升级（SSE + enableChunked） | P1 | 同上（stream=true） |
| F2-05 | 本地危机词库同步拦截 | P1 | 同上（crisis 事件） |
| F2-06 | 回复点赞/点踩 | P1 | POST /messages/{id}/feedback |
| F4-01 | 模型异步风险判定与分级响应 | P4 | 同上（risk_level） |

## 2. 任务卡片字段（Issue / 任务系统）

每条任务必须包含：

- **编号 + 标题**：动词开头，如"完成微信登录换取 JWT 全链路"。
- **所属阶段**：P0–P5，用于对齐里程碑。
- **关联接口**：API 文档中的路径；接口不存在时标注 [契约待补]，先与 API 文档同步。
- **验收标准**：来自《开发文档》对应功能"规则约束 / 边界与异常"，可验证。
- **优先级**：P0（必须）/ P1（重要）/ P2（可选）。
- **状态流转**：待办 → 开发中 → 待验收 → 已完成。

## 3. 拆分原则

- 一个任务 = 一个可独立交付的逻辑变更，可单独验收。
- 任务不跨阶段：跨阶段的工作拆成多条。
- 每条任务对应独立分支：`feature/<阶段>-<编号>-<slug>`，如 `feature/p1-f2-01-auth-login`。
- 合入 `main` 即视为完成，须满足完成定义（DoD）。

## 4. 完成定义（DoD）

任务标记"已完成"前必须全部满足：

- [ ] 代码合入 `main`（通过评审与 CI，若已配置）
- [ ] 后端测试通过（pytest 全绿），危机/认证/删除类改动带测试
- [ ] 接口行为与《API 文档》一致；不一致时已同步更新文档
- [ ] 提交信息符合 Conventional Commits（见 CONTRIBUTING）
- [ ] 安全红线自查：无密钥入库、无敏感信息进日志、user_id 隔离

## 5. 看板与节奏

- 以周为节奏：每周一确认本周任务（对齐阶段），周五核对验收。
- 每个阶段验收通过后打里程碑 tag（m1–m5），未完成的任务不得带入下阶段主干。
